INTEGRATION AND IFRAME OUTLINE
==============================

Purpose
-------
This workspace runs several independently built frontend/backend modules as
one local Business Center system. The main React application is the host
application. It embeds the Staff ID Management frontend inside the host's
ID Management route.


1. LOCAL SERVICE MAP
--------------------

Docker Compose creates one shared bridge network (integrated-network) and one
MySQL 8 database (business_center). Every Laravel backend connects to that
database through the Docker service name "mysql".

Browser-facing local URLs (from .env):

  Main Business Center
    Frontend: http://localhost:5173
    API:      http://localhost:8000/api

  Staff ID Management
    Frontend: http://localhost:5174
    API:      http://localhost:8001/api

  Student Print
    Frontend: http://localhost:5175
    API:      http://localhost:8002/api/v1

  Staff Sticker
    Frontend: http://localhost:5176
    API:      http://localhost:8003/api

  Student Account
    Frontend: http://localhost:5177
    API:      http://localhost:8004/api

  Infrastructure
    MySQL:      localhost:3306
    phpMyAdmin: localhost:8080


2. FRONTEND INTEGRATION MODEL
-----------------------------

Main React frontend (main-system/react-frontend)
  - Owns the browser route, session context, staff navigation, and outer page
    shell.
  - ProtectedRoute renders MainLayout for authenticated users.
  - The /staff-management route renders StaffManagement.jsx.
  - StaffManagement.jsx displays the Staff ID frontend in an iframe.

Staff ID frontend (staff_id_managament/frontend)
  - Is a separate Vite/React application.
  - Its App.jsx renders StaffDashboard.
  - StaffDashboard renders one of these workflow tabs:
      * student-records  -> StaffStudentRecords
      * id-management    -> StaffIdGeneration
      * id-status         -> StaffIdStatus
      * release-history   -> StaffReleaseHistory
  - When embedded, it hides its own top navigation and uses the host's tabs.

The iframe source is configured in the main frontend service:

  VITE_STAFF_ID_URL = http://localhost:5174

StaffManagement.jsx uses this value for both:

  <iframe src={STAFF_ID_URL} ... />
  postMessage(..., STAFF_ID_URL)


3. IFRAME AUTHENTICATION FLOW
-----------------------------

The two frontends have different origins because their ports differ. Browser
localStorage is origin-specific, so the iframe cannot read the host app's
auth_token directly. The host forwards the existing token with postMessage.

Flow:

  1. A logged-in staff user opens /staff-management in the main app.
  2. StaffManagement renders the iframe at http://localhost:5174.
  3. The iframe detects that it is embedded:

       window.self !== window.top

  4. The iframe sends REQUEST_AUTH_TOKEN to window.parent.
  5. The host receives the request, verifies that event.origin equals
     VITE_STAFF_ID_URL, reads its auth_token from localStorage, and sends:

       { type: 'AUTH_TOKEN', token }

     to the iframe using VITE_STAFF_ID_URL as targetOrigin.
  6. The iframe saves the token in its own origin's localStorage.
  7. The iframe calls GET /user through its own Staff ID API client.
  8. The API client adds this header to subsequent Staff ID API requests:

       Authorization: Bearer <token>

  9. The Staff ID dashboard loads the selected workflow and its data.

The host also sends the token immediately and again after the iframe load
event. This covers both possible startup orders: the host can be ready before
the iframe, or the iframe can request the token first.


4. IFRAME TAB SYNCHRONIZATION
-----------------------------

The parent page owns the visible tab strip. The child owns the tab content.
They keep the selected tab synchronized with postMessage.

Host-to-iframe
  - User clicks a host tab.
  - StaffManagement updates its activeTab state.
  - It sends:

      { type: 'CHANGE_TAB', tab }

  - StaffDashboard receives the message and updates its activeTab state.

Iframe-to-host
  - If the iframe changes a tab itself, StaffDashboard sends:

      { type: 'TAB_CHANGE', tab }

  - StaffManagement verifies the iframe origin and updates its activeTab.

Supported tab identifiers:
  - student-records
  - id-management
  - id-status
  - release-history


5. DATA AND API BOUNDARIES
--------------------------

Main frontend
  - Uses VITE_API_URL (the main Business Center API).
  - Handles the main Business Center screens such as POS, Orders, Rentals,
    Print Orders, and the outer ID Management page.

Staff ID frontend
  - Uses VITE_API_URL set to the Staff ID API.
  - api/client.js gets auth_token from the Staff ID origin's localStorage.
  - apiRequest() sends Accept: application/json and, when available,
    Authorization: Bearer <token>.
  - It uses credentials: include for requests.

Backend integration
  - Each backend is an independent Laravel service.
  - The services share the MySQL database but retain their own API URLs and
    frontend deployments.
  - CORS_ALLOWED_ORIGINS includes all five local frontend origins so browser
    requests from those frontends can reach their APIs.


6. LOADING BEHAVIOR
-------------------

The main host mounts the iframe immediately.
The child shows a page-shaped skeleton while it is waiting for the forwarded
token or for the authenticated dashboard data to load. Once authentication is
complete, each Staff ID workflow uses its own table/card skeleton while its
data request is pending.


7. CURRENT SECURITY NOTES
-------------------------

Existing protection
  - The host only accepts iframe messages when event.origin exactly matches
    VITE_STAFF_ID_URL.
  - The host sends AUTH_TOKEN and CHANGE_TAB with an explicit targetOrigin.

Recommended hardening
  - In StaffDashboard.jsx, validate event.origin before accepting AUTH_TOKEN
    or CHANGE_TAB. It currently accepts messages from any origin.
  - Replace the iframe's REQUEST_AUTH_TOKEN targetOrigin of "*" with the
    configured main frontend origin (for local development, http://localhost:5173).
  - Keep VITE_STAFF_ID_URL as an origin only (scheme + host + port), without a
    path, because it is used as a postMessage targetOrigin.
  - In production, use HTTPS and production-specific allowed CORS origins.


8. KEY FILES
------------

  compose.yaml
    Service definitions, container networking, volumes, and frontend/backend
    environment-variable injection.

  .env
    Local ports, browser URLs, API URLs, and CORS origin list.

  main-system/react-frontend/src/App.jsx
    Registers /staff-management inside the protected main application.

  main-system/react-frontend/src/pages/StaffManagement.jsx
    Creates the iframe, forwards the token, and synchronizes tabs.

  staff_id_managament/frontend/src/App.jsx
    Starts the embedded StaffDashboard application.

  staff_id_managament/frontend/src/pages/StaffDashboard.jsx
    Detects iframe mode, receives auth/tab messages, and renders workflow tabs.

  staff_id_managament/frontend/src/api/client.js
    Adds the stored bearer token to Staff ID API requests and handles 401 errors.
